Accessibility

This page documents the specific design choices I made to make this portfolio accessible — and what I learned in the process.

My Commitment

Accessibility is not an afterthought — it is a design value. Building this portfolio, I tried to apply what we discussed in class about who gets to participate in digital spaces, and to make deliberate choices that lower barriers to access rather than raise them.

The Wave extension audit (used in Week 8) surfaced issues I had not noticed. Here is what I found, what I fixed, and what remains imperfect.

Specific Changes I Made

Skip Link

Every page has a "Skip to main content" link as the first focusable element. It is visually hidden until focused, so keyboard users can bypass the navigation without tabbing through every menu item.

Why: Screen readers and keyboard-only users would otherwise have to navigate the full header on every page load.

Semantic HTML Structure

Every page uses proper landmark elements: <header>, <nav>, <main>, <footer>, and <section> with aria-labelledby attributes. Headings follow a strict H1 → H2 → H3 hierarchy — no skipped levels.

Why: Screen readers use landmark and heading structure to navigate pages non-linearly. Without it, the page is experienced as an undifferentiated wall of text.

Descriptive Alt Text

Every image in the portfolio has alt text describing what it shows and why it matters in context — not just "image" or a filename. Decorative elements use alt="" so screen readers skip them.

Why: Alt text is the primary way visually impaired users access image content. Generic alt text is no better than none.

Color Contrast

The site uses a high-contrast dark ink (#1a1612) on cream background (#f5f0e8) — contrast ratio of approximately 14:1, well above the WCAG AA threshold of 4.5:1. The accent color (#c8441a) is used for decorative emphasis only, never as the sole carrier of meaning.

Why: Low contrast is one of the most common and most impactful accessibility failures, affecting users with low vision, color blindness, and users in bright-light environments.

Keyboard Navigation

All interactive elements — links, buttons, the mobile nav toggle — are reachable and operable via keyboard. Focus states are visible (a 2px accent-colored outline) and never suppressed with outline: none.

Why: Many users navigate entirely by keyboard, including users with motor disabilities and power users. Invisible focus states make a site unusable for them.

Responsive Design

The layout adapts to mobile screen sizes using CSS media queries and flexible grid layouts. Text remains legible at all sizes. The navigation collapses to a hamburger menu on small screens with proper ARIA attributes (aria-expanded).

Why: A site that only works on desktop excludes users who rely on mobile devices as their primary or only access to the web.

What I Learned

Before this class, I thought about accessibility the way I thought about AI — as someone else's problem. Building this site taught me that accessibility is a design choice made (or not made) by the person building the thing. Every image without alt text, every low-contrast color choice, every inaccessible embed is a decision — usually an invisible one — to exclude someone.

This connects to D'Ignazio and Klein's argument in Data Feminism about who counts as a user. The default user in most web design is sighted, mouse-using, neurotypical, and English-speaking. Building accessibly means questioning that default — the same critical reflex the course asked us to apply to AI.
